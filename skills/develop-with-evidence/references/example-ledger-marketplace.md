## Summary

Pages fetched, in order: `pc-saas-fulfillment-subscription-api` (primary — Resolve, Activate, Get, status enum, all status-code tables), `pc-saas-fulfillment-apis` (flow overview, confirms only backend service-to-service calls are supported), `saas-fulfillment-apis-faq` (searched specifically for throttling/429/Retry-After — none found), `pc-saas-fulfillment-life-cycle` (defines what each `saasSubscriptionStatus` value means, confirms `Subscribed` is the only billable/active state), `pc-saas-registration` (token acquisition: endpoint, scope, headers, 1-hour expiry).

What changed in the design because of the docs: the original plan was "call Activate, if 200 return active:true." The docs' own words on Activate's 200 ("Request ... is received ... This operation gives you the definitive answer" attached to the *Get* call, not Activate) forced a two-step design — Activate then poll Get — otherwise the adapter would report `active: true` for subscriptions that are still `PendingFulfillmentStart` or that fail asynchronously (Activate failure "automatically sends an 'Unsubscribe' webhook", i.e., it can fail *after* the 200). Similarly, Activate's 400/404 codes turned out to carry specific state meanings (already-Suspended / already-Unsubscribed) rather than being generic errors, so those are handled as outcomes, not exceptions.

What remains a gap: throttling behavior (whether 429/Retry-After is even used by this API, and any documented backoff policy) is not stated on any fulfillment-API page found; the module honors `Retry-After` when present (general HTTP semantics) and falls back to a constant, both marked `UNVERIFIED_`. The exact poll interval/attempt count after Activate ("a few minutes") is likewise undocumented and pinned to `UNVERIFIED_` constants with a test that names the behavior undocumented. Token acquisition (the Entra client-credentials call) is documented but deliberately not implemented in this module — see NOTES.md.
